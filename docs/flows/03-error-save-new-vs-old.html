New error vs old error: exactly what is written to the database

Every diagnose call writes an audit row. An “old” error only increments a counter on an existing cluster. A “new” error inserts a cluster row plus its Titan vector. Solution links are upserted only when hybrid search returned notes above the 70% bar. The pasted raw text is never used as the cluster’s stored identity.

Decision in one line. Vector similarity ≥ 0.70 (raw or generalized) or SHA-256 of generalized text already exists → OLD else → NEW. Then always → error_events.

Decision tree

Pass 1 or 2 hit
OLD via vector. _touch_distinct(hit.id). No new embedding. LLM generalize output (if pass 2 ran) is discarded except that we already used its text for the search. Working generalized text is replaced by the cluster’s stored generalized_text.
Both passes miss
Call _create_distinct(title, generalized, family_code, summary) with the LLM generalize result. First it looks up fingerprint_hash.
Fingerprint exists
OLD via exact hash. Same _touch_distinct. Happens when two pastes generalize to the identical string but their vectors scored < 0.70 (unusual, but coded). created_new stays false. Title/summary/family from this LLM call are not applied to the row.
Fingerprint new
NEW cluster. INSERT distinct_errors, then INSERT distinct_error_embeddings. created_new = True. match_percent stays 0.0 (it is never set on this branch).
Every request
INSERT error_events with the raw paste, chosen cluster id, family, match percent, created_new flag, caller, source.
Notes ≥ 70%
UPSERT error_cluster_solutions (cluster ↔ summaries.id). Feeds the cluster graph. Informational families never reach this. Zero notes → LLM fallback string in the JSON only — not stored as a note.

What “new” writes — _create_distinct

1. Fingerprint

fingerprint_hash = sha256( generalized_text.strip().encode("utf-8") ).hexdigest()

It is a unique key on distinct_errors. Same generalized string cannot create two clusters.

2. Cluster row

INSERT INTO distinct_errors (
  fingerprint_hash, title, generalized_text, summary, family_code,
  occurrence_count, first_seen_at, last_seen_at
) VALUES (?, ?, ?, ?, ?, 1, ?, ?)
RETURNING *
ColumnSource
titleLLM generalize title (or "Integration error")
generalized_textLLM generalized_text (or regex-cleaned raw if no API key)
summaryLLM summary
family_codeRegex-first, then LLM catalog code, else UNCLASSIFIED_ERROR
occurrence_countAlways 1 on insert
first_seen_at / last_seen_atSame IST timestamp

The raw pasted error is not a column on distinct_errors. It only lives on error_events.raw_text.

3. Cluster embedding row

blob = "TITLE: {title}\n\nGENERALIZED: {generalized}\n\nSUMMARY: {summary}"
content_hash = sha256(blob)
emb = Titan V2 (1024-dim, normalized)
vec = "[f0,f1,...]"

INSERT INTO distinct_error_embeddings
  (distinct_error_id, content_hash, embedding, model, created_at, updated_at)
VALUES (?, ?, ?::vector, ?, ?, ?)

One-to-one with the cluster (distinct_error_id unique, ON DELETE CASCADE). There is no ON CONFLICT here — create is insert-only.

Solution links — only when notes matched

For each hybrid-search hit that survived the 70% filter:

INSERT INTO error_cluster_solutions
  (distinct_error_id, summary_id, match_percent, last_seen_at)
VALUES (?, ?, ?, ?)
ON CONFLICT (distinct_error_id, summary_id) DO UPDATE SET
  match_percent = EXCLUDED.match_percent,
  hit_count = error_cluster_solutions.hit_count + 1,
  last_seen_at = EXCLUDED.last_seen_at
  • Runs for both old and new clusters. First time a note is linked: hit_count defaults to 1. Later diagnoses of the same pair increment it and refresh percent.
  • summary_id is the hybrid hit’s id. The FK points at summaries(id) (SAP Notes). Community hits share the same JSON id space but a different table — a community-only id will fail the FK or collide with a note id.
  • The HTTP response then slims solutions (drops note numbers). The graph API still reads this link table.
  • LLM fallback markdown is returned as fallback_solution and is not inserted anywhere.

Side-by-side

Old error (seen before)

  1. UPDATE distinct_errors count + last_seen
  2. INSERT error_events (created_new=0, match % from vector)
  3. Maybe UPSERT error_cluster_solutions

0 rows added to embedding tables.

New error (first of its kind)

  1. INSERT distinct_errors (count = 1)
  2. Titan of TITLE/GENERALIZED/SUMMARY blob
  3. INSERT distinct_error_embeddings
  4. INSERT error_events (created_new=1, match % = 0)
  5. Maybe UPSERT error_cluster_solutions

There is no “raw errors” table of unique pastes. Duplicates of the same failure collapse into one cluster. History of each paste is error_events. The cluster is the DNA; the event is the occurrence.
