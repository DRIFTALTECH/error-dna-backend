When someone sends just an error: every embedding step

POST /api/errors/diagnose never embeds the error “into the notes table.” It embeds the pasted text with Titan V2, then measures cosine similarity against distinct_error_embeddings — a different vector table from SAP Notes. Notes are searched later, with a second (sometimes third) Titan call, against summary_embeddings.

Two vector stores. Do not mix them.
distinct_error_embeddings = known error clusters (have we seen this failure before?).
summary_embeddings = SAP Note / Community fixes (which solution text is closest?).

Entry point — nothing is skipped

  1. Client sends POST /api/errors/diagnose with Bearer (UI JWT or OAuth client_credentials).
  2. routes/errors.py validates error_text (min length 1) and optional source.
  3. diagnose(raw_error, caller, source) in services/error_diagnose.py runs the chain below.

Pass 1 — embed the raw error, search clusters

1.1
strip

raw = error_text.strip(). If empty, raise ValueError("error_text is required"). Locals start as: created_new=False, match_percent=0.0, generalized=raw, gen=None.

1.2
Titan #1

_vector_search(raw) calls embed_text(raw) on a thread. Same function notes use. Payload:

{
  "inputText": "<the exact pasted error, no TITLE:/FAMILY: wrapper>",
  "dimensions": 1024,
  "normalize": true
}

Model: amazon.titan-embed-text-v2:0. Output: 1024 floats. Converted to '[0.12,-0.03,...]' because asyncpg cannot send a Python list as vector.

1.3
SQL

That query vector is bound twice (once for the similarity expression, once for ORDER BY):

SELECT de.id, de.title, de.generalized_text, de.summary, de.family_code,
       de.occurrence_count,
       (1 - (dee.embedding <=> $1::vector)) AS similarity
FROM distinct_error_embeddings dee
JOIN distinct_errors de ON de.id = dee.distinct_error_id
ORDER BY dee.embedding <=> $1::vector
LIMIT $2   -- ERROR_VECTOR_SEARCH_LIMIT, default 5

<=> is pgvector cosine distance. Titan vectors are normalized, so cosine similarity ≈ 1 − distance. Each row is clamped to [0.0, 1.0].

1.4
threshold

_best_match(hits) looks only at hits[0] — already the nearest neighbor.

  • No rows → miss.
  • hits[0].similarity >= ERROR_MATCH_THRESHOLD (default 0.70) → hit. Cluster found.
  • Closest neighbor is 0.69 → treated as a complete miss. Neighbors 2–5 are never used as a fallback match.
1.5
if hit

Pass 2 is skipped. No LLM generalize. The code bumps the cluster (see briefing 03) and copies distinct_row.generalized_text into the working generalized variable — the caller’s raw text is not kept as the cluster identity. match_percent = round(similarity * 100, 1).

Pass 2 — only if pass 1 missed

2.1
regex first

generalize_error(raw) always runs classify_text(raw) first: walk error_families.match_patterns by match_priority, first regex hit wins. Catch-all .* is deferred. Empty text → UNCLASSIFIED_ERROR.

2.2
LLM generalize

If LLM_API_KEY is set, DeepSeek is asked to strip user ids, tenant ids, timestamps, correlation ids, GUIDs, IPs, host paths, and keep the technical meaning. Temperature 0.2, up to 16384 tokens, 60s timeout, JSON object.

{
  "title": "descriptive label",
  "generalized_text": "stable generic form of the full error",
  "summary": "root-cause / context for search",
  "family_code": "CODE_FROM_CATALOG"
}

Family rule: if the regex already found a real family, regex wins over the LLM. Else use the LLM code if it is in the catalog. Else UNCLASSIFIED_ERROR.

If the API key is missing, a tiny regex strips UUIDs and S-user ids (S\d{7,10}) and that cleaned string is used as title, generalized_text, and summary.

2.3
Titan #2

_vector_search(generalized_text) — a new embedding of the generalized string, not a reuse of the raw-error vector. Same SQL, same LIMIT 5, same 0.70 test.

2.4
if hit

Same as 1.5: touch the cluster, adopt its stored generalized text, set match_percent. The LLM title/summary from this call are not written onto the existing cluster.

Pass 3 — both searches missed: embed a new cluster blob

If pass 2 never ran (theoretically: pass 1 miss but gen still None), generalize is called now. Then _create_distinct(title, generalized, family_code, summary).

Query vector ≠ stored vector format. Pass 1 and 2 embed the error string as-is. A new cluster stores Titan of this blob: 
TITLE: {title}

GENERALIZED: {generalized_text}

SUMMARY: {summary}
Matching still works because Titan is semantic, but the stored point is a richer document than the query. Future searches of similar raw errors are compared against this blob embedding, not against a raw-error embedding.
  1. Fingerprint = SHA-256 of generalized_text.strip(). If that hash already exists, it is treated as old (no new embedding). See briefing 03.
  2. Otherwise INSERT distinct_errors.
  3. Build the blob above. SHA-256 it (content_hash).
  4. Titan #3 embed_text(blob) in a thread.
  5. INSERT into distinct_error_embeddings (distinct_error_id, hash, ?::vector, model, timestamps). No upsert — one vector row per cluster.

Solution search — a separate embedding against SAP Notes

After a cluster is chosen or created:

  1. Resolve family_name from family_code.
  2. If family_code == INFORMATIONAL_FAMILY_CODE (default RUN_DIAGNOSTIC_EVENT): skip all of this. No Titan, no notes, no LLM fallback.
  3. Query string = generalized, else cluster title, else original raw.
  4. hybrid_search(query, limit=ERROR_SOLUTION_LIMIT) (default 10, max 20).

Inside hybrid_search — exact embedding steps

S.1
Titan again

_vector_hits embeds the query string (generalized error), not the cluster blob and not the raw paste (unless those are what query is).

S.2
notes SQL 
SELECT source, summary_id,
       (1 - (embedding <=> $1::vector)) AS similarity
FROM summary_embeddings
ORDER BY embedding <=> $1::vector
LIMIT 20   -- HYBRID_CANDIDATE_LIMIT

This table holds both source='notes' and source='community'. Family is not a filter. If Bedrock throws, vector hits become [] and search continues keyword-only.

S.3
keyword

Parallel ILIKE %query% on latest summaries and community_summaries (title, issue, summary, tags). Python then scores: full-query in title = 1.0, in issue = 0.85, tags = 0.75, summary = 0.55; else token overlap × 0.4.

S.4
blend
  • Both scores > 0 → 0.7 × vector + 0.3 × keyword
  • Vector only → vector score
  • Keyword only → keyword score

Sort descending. Load full summary rows. match_percent = round(score * 100) as an integer.

S.5
filter again

Diagnose keeps only hits with match_percent >= 70 (same 0.70 threshold × 100). So a note at 65% from hybrid search is dropped even though hybrid returned it.

If any remain → persist cluster↔note links (briefing 03) and return them as slim solutions (title, problem, fix, cautions, match_percent — no SAP note numbers in the diagnose JSON).

If zero remain (and not informational) → LLM fallback (ZHC prompt in prompts.py). That call does not produce or store an embedding.

How many Titan calls can one paste trigger?

SituationTitan callsWhat is embedded
Raw text matches a cluster ≥ 70%2(1) raw error vs clusters (2) generalized/title/raw vs notes
Raw miss, generalized hits a cluster3(1) raw (2) generalized vs clusters (3) query vs notes
Both miss, new cluster, notes found4(1) raw (2) generalized vs clusters (3) new cluster blob (4) query vs notes
Informational family1–3Cluster search only. Notes embedding skipped.

If pass 1 hits, generalize never runs, so the notes query is the cluster’s stored generalized_text (step 1.5), not a freshly generalized version of this paste.

What this path does not do

  • It does not embed into summary_embeddings on diagnose. That table is write-on-scrape only.
  • It does not re-embed an existing cluster when a known error arrives. The stored vector stays the original blob.
  • It does not filter notes by family_code.
  • It does not compare raw text with SQL LIKE against distinct_errors. Cluster identity is vector (plus a fingerprint only when creating).
